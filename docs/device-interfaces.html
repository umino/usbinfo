インターフェイスと devnode

別々のデバイスインターフェイスクラス (GUID) で列挙しても、たどった先の devnode が同じになることがあります。そのとき何が同じで何が違うかをまとめます。

被るか被ります。1 つの devnode が、複数のインターフェイスクラスを登録できるためです。光学ドライブとフロッピーがその例です。

同じかdevnode に付いている値 (DevInst が指す先、セットアップクラス、デバイスのプロパティ) は同じです。インターフェイスに付いている値 (GUID、DevicePath、有効かどうか) は違います。

開くとどちらの DevicePath を CreateFile しても、同じデバイススタックに I/O が届きます。IOCTL の結果も通常は同じです。

前提

インターフェイスは「入口」、devnode は「実体」

devnode はデバイスツリー上のノードで、1 台のデバイス (または論理的なデバイス) を表します。デバイスインターフェイスは、ドライバーがその devnode に登録する「アプリから開くための入口」です。入口にはそれぞれ種類 (インターフェイスクラスの GUID) と、開くためのパス (DevicePath) があります。

ドライバーは 1 つの devnode に、対応する機能の数だけ入口を登録できます (Overview of Device Interface Classes)。

補足

どちらの DevicePath を開いても同じ結果になる理由

ドライバーはインターフェイスを、devnode の PDO (デバイススタックの最下段) に対して登録します (IoRegisterDeviceInterface の PhysicalDeviceObject)。どの入口から開いても I/O は同じスタックの最上段から流れるので、IOCTL_STORAGE_GET_DEVICE_NUMBER などの結果も同じになります。

例外は、登録時に「参照文字列 (reference string)」を付けた場合です。参照文字列はパスの一部になり、ドライバーは開かれた入口ごとに振る舞いを変えられます。ドキュメントには、使うのは swenum など一部のバスドライバーだけとあります。ストレージのクラスドライバーには当てはまらないと考えています。

このプロジェクトのコードとの関係

  • 光学ドライブ・フロッピーの判定 (ownsDriveInterface / isDriveOwnedVolume): 図 1 の性質を使っています。ボリュームの devnode が CDROM か FLOPPY のインターフェイスも登録していれば、ドライブ自身と判定します。
  • ボリュームとドライブの対応付け (volumeBelongs): DevInst の数値ではなく、インスタンス ID の文字列で比べています。上の表に照らしても安全な方法です。
  • -f letters の Diff 列 (compareDriveSelection): 既存方式と新方式で別々に列挙した DevInst を、数値で比べています。実装上はおそらく同じ値になりますが、ドキュメント上の保証はありません。
